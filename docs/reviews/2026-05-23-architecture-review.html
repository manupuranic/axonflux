Architecture Review · 2026-05-23

AxonFlux — Deepening Opportunities

Survey of shallow modules, leaky seams, and untestable interfaces. Each candidate proposes a deepening — turning interfaces with high implementation-to-interface ratio into modules where one small interface hides a lot of behaviour.

Headline findings

What's deep

Cash Closure tool plugin · Pamphlets service layer · BOM-aware step 04 SQL · derived layer rebuild contract

What's shallow

Analytics router (SQL = business logic) · Schema sync between Python/TS · Script infrastructure (6× reinvention)

What's leaky

BOM router (raw SQL on app+raw schemas) · Pipeline step ordering (implicit, by filename) · Schema drift (untyped)

1 · Extract a Read-Query Module

Strong

SQL is leaking from derived.* reads up through every read-only router. Each route IS the business logic — there's no seam to test against.

Files involved

  • api/routers/analytics.py · 533 LOC, 15 text()
  • api/routers/customers.py · 382 LOC, 8 text()
  • api/routers/products.py · 264 LOC, 5 text()
  • api/routers/suppliers.py · 76 LOC, 3 text()

Friction

  • · 70–100 line SQL strings embedded in route handlers
  • · Can't unit-test the query independent of HTTP transport
  • · Same derived.* table queried with slight variations across endpoints
  • · FastAPI route handler IS the data access layer

  def revenue_7d(self) -> Decimal: ...

Why this is deep

  • Test surface: Query module returns typed objects testable with seed data — no HTTP/JWT/FastAPI machinery required.
  • Deletion test: Deleting api/queries/ would scatter ~30 SQL strings back across 4 routers. Complexity concentrates when consolidated. Pass.

2 · Declare Pipeline Step Dependencies

Strong

Step ordering enforced only by filename prefix. Step 04 reads app.product_bom but never declares the dependency. If 04 runs before 01, you get silent data corruption — no error.

Files involved

  • pipelines/weekly_pipeline.py · lines 29–41
  • sql/rebuild_derived/00..10_*.sql
  • sql/rebuild_derived/04_product_stock_position.sql · joins app.product_bom + derived.product_daily_metrics

Failure mode

  • · No error on missing dependency — just zero BOM consumption
  • · pseudo_stock = purchased − sold (missing the BOM drain)
  • · Downstream step 06 (replenishment) uses corrupted stock
  • · Failure invisible until staff notices replenishment is wrong

BEFORE — Implicit order, no contract

Shape of the solution

Each .sql file gets a header comment or a sibling .toml declaring its inputs. A Python PipelineStep dataclass reads them, builds a DAG, validates topological order at pipeline start, fails fast if a step depends on a missing table.

-- sql/rebuild_derived/04_product_stock_position.sql
-- requires: derived.product_daily_metrics  (step 01)
-- requires: app.product_bom                (alembic-managed)
-- produces: derived.product_stock_position
CREATE TABLE IF NOT EXISTS derived.product_stock_position (...);
  • Leverage: Pre-flight validator catches missing dependencies before any step runs.
  • Locality: Each SQL file declares its own contract — no central manifest to drift.
  • Test surface: Parser is pure; DAG validation is testable without DB.
  • Deletion test: Without declared deps, ordering is filename convention. A junior dev renaming files breaks the pipeline silently. Strong pass.

3 · Generate TS Types from Pydantic

Strong

~60 Pydantic schemas duplicated in TypeScript by hand. Drift is invisible — there's at least one real bug already (SuggestionCluster's AliasResponse vs SuggestionItem).

Files involved

  • api/schemas/*.py · ~15 files
  • api/tools/**/schemas.py · 4 files
  • web/types/api.ts · 434 LOC, manually mirrored

Known drift

  • · SuggestionCluster.suggestions: Python = list[AliasResponse], TS = SuggestionItem[]
  • · Manual sync after every schema change
  • · Compile passes even when TS is wrong
  • · Runtime shape mismatch = silent UI bug

4 · BOM Tool — Extract Service Layer

Worth exploring

BOM router (322 LOC, 10 embedded SQL strings) violates the tool plugin contract that Cash Closure follows. Mixes raw schema reads with app schema writes through the wrong dependency (Session instead of Connection).

Pattern divergence across tools

ToolService?SQL in router?
cash_closure✓none
pamphlets✓none
entity_resolution✓subprocess spawn
bom✗10× text()

Friction

  • · Cannot unit-test BOM business logic (qty validation, name resolution, conflict detection)
  • · Reads raw.raw_sales_itemwise through ORM Session (wrong tx semantics)
  • · Future agents (D7 Image Agent, D8 Content Writer) cannot reuse BOM logic — only HTTP layer
  • · The pattern Cash Closure proved works, but BOM didn't follow it

BEFORE — SQL in router

@router.post("/confirm")
def confirm_bom(body, db: Session):
    if body.qty_per_unit <= 0: raise HTTPException(...)
    raw_name = db.execute(text("""
      SELECT MAX(item_name_raw) FROM (
        SELECT item_name_raw FROM raw.raw_sales_itemwise
        UNION ALL
        SELECT ... -- mixed schema query
      ) t WHERE barcode=:bc
    """), {"bc": body.raw_barcode}).scalar()
    existing = db.execute(text("""
      SELECT id FROM app.product_bom
      WHERE raw_barcode=:r AND finished_barcode=:f
    """), {...}).scalar()
    if existing: raise HTTPException(409, ...)
    row = db.execute(text("""
      INSERT INTO app.product_bom ...
    """), {...}).mappings().one()
    if body.suggestion_id:
        db.execute(text("UPDATE ..."), {...})
    db.commit()
    return BomMapping(...)

AFTER — Service module

bom/router.py

@router.post("/confirm")
def confirm_bom(body, svc=Depends(get_bom_service)):
    return svc.confirm(body, current_user)

bom/service.py

class BomService:
  def confirm(self, req, user) -> BomMapping:
    self._validate_qty(req.qty_per_unit)
    self._reject_if_duplicate(req)
    raw_name = self.name_resolver.resolve(req.raw_barcode)
    fin_name = self.name_resolver.resolve(req.finished_barcode)
    mapping = self.repo.insert(req, user, raw_name, fin_name)
    if req.suggestion_id:
      self.repo.mark_suggestion_confirmed(req.suggestion_id)
    return mapping
  • Leverage: Router becomes 1-line delegations. Business rules (qty > 0, no duplicates, suggestion lifecycle) live in one testable place.
  • Locality: Future BOM rule changes (e.g., enforce qty ≤ 100) touch service only, not the HTTP layer.
  • Test surface: BomService.confirm() testable with stub repo + in-memory name resolver. Currently zero unit tests possible.
  • Deletion test: Without service extraction, BOM stays a 322-line router. Pass.

6 · Frontend API client — split by domain

Speculative

web/lib/api.ts is 429 lines, one giant api = { ... } object. ~60 endpoints flat at the root level. Works, but doesn't help discoverability.

Friction

  • · Adding an endpoint = scrolling 429 lines to find the right spot
  • · Refactoring a domain (e.g. customers) touches a 400-line file
  • · No code-splitting opportunity — every page imports everything

Note

This is speculative because if Candidate 3 (codegen) lands, the manually-written api.ts may become moot — the generated client takes over. Defer this until codegen lands; revisit if the generated client is awkward.

Top recommendation

Start with Candidate 2 — Pipeline dependency declaration

Three candidates are Strong. Pick this one first because it's the only one where the current state can silently corrupt production data. Step 04 reads app.product_bom with zero declared dependency. If a future engineer reorders the SQL files, the BOM consumption silently disappears from stock position, and the replenishment sheet starts recommending reorders for products that don't need them. There is no test that catches this.

It's also small and contained: a header comment grammar in the SQL files + a Python parser + a pre-flight DAG check in weekly_pipeline.py. One day of work. Defends every future SQL step automatically.

After Candidate 2 lands

Then Candidate 3 (codegen) — catches schema drift before it ships.

Then

Candidate 1 (read-query module) — biggest LOC delta, but lowest risk because read-only.
