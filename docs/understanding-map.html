Ingestion

Raw Ingestion Layer

Converts binary Er4u exports into structured database rows. A generic ingest_raw_table() handles all six report types through a HEADER_MAP plus reader function pattern. Chunked at 2000 rows — this is a memory bound, not a performance tuning.

HEADER_MAP drift. Er4u changes a column name silently and ingestion fails without alerting downstream.
Raw Schema

The Immutable Source of Truth

Append-only audit log. Every row tagged with import_batch_id (UUID) and source_file_name. SHA-256 deduplication at the file level. No foreign keys between raw tables — by design. Raw data is dirty; the raw layer stores reality as exported, not as it should be.

No row-level validation. A negative quantity or zero price enters silently and propagates through every downstream calculation.
Derived Schema

The Rebuildable Analytics Layer

Ten-step SQL rebuild. TRUNCATE then INSERT on every run. Step 01's dense product×date grid is the foundation — every step that follows depends on it. Window functions compute features. Business rules become SQL flags. No application state lives here.

No transaction wraps the full rebuild. If the pipeline crashes at step four, you have partially rebuilt tables and a confused frontend.
API

The FastAPI Backend

Two connection patterns deliberately split: raw text() SQL for derived.* and raw.* reads, SQLAlchemy ORM for app.* writes. The pipeline is never imported — it runs as a subprocess. JWT auth with 480-minute expiry. Tool plugin auto-discovery means new tools mount without touching main.py.

A subprocess pipeline crash isn't surfaced unless the frontend polls logs. Silent failures are possible.
App Schema

The Application State Layer

Human-authored data that must survive pipeline rebuilds. Canonical product names, alias mappings, run history, cash closures, pamphlets. The COALESCE enrichment pattern is critical: app data overrides derived at query time, never by modifying derived tables.

A confirmed bad alias permanently corrupts all historical metrics for that barcode. No undo mechanism.
Frontend

The Next.js Dashboard

App Router, React 19, two route groups: (auth) public, (internal) protected. No global state manager — fetch per page with JWT from localStorage. Recharts for time series. shadcn/ui components copied into the repo (not a library; a code generator).

JWT in localStorage is XSS-exposed. httpOnly cookies would be safer.

The ten-step
SQL pipeline.

Each step feeds the next. Step 00 anchors the date range; Step 01 is the foundation everything builds on. Break any step, break everything downstream.

00

Daily Sales Summary

Aggregates raw_sales_itemwise and billwise. One row per day — revenue, bills, items sold.

→ Anchors MIN(date) for Step 01's date spine

01

Product Daily Metrics ★

Dense grid: every product × every date. Cross-join generates zeros for no-sale days. Alias remapping folds duplicate barcodes. ~2.3M rows.

→ Foundation for every downstream step

02

Product Daily Features

lag_1, lag_7, rolling 7/30/60-day average, stddev, stockout_proxy, calendar joins (holidays, festival distance).

⚠ Data leakage: CURRENT ROW window includes today

03

Health Signals

Weighted demand forecast: 0.6 × last7 + 0.3 × last30 + 0.1 × last60. Four flags: fast / slow / dead / spike. Floor at 0.02.

→ Drives every replenishment recommendation

04

Stock Position

Cumulative SUM(purchases) − SUM(sales) via unbounded window. Pseudo-stock can go negative; no opening stock known.

→ Used by Step 06 for days-of-cover calculation

05

Necessary Views

Dimension views: product_dimension, supplier_location, latest_item_combinations, product_supplier_mapping.

→ Referenced by Steps 06, 07, 08

06

Supplier Restock Recommendations

Days of cover = stock ÷ demand. Min stock = 7× demand. Max = 30× demand. Lead times: 7d for Bellary, 15d others — hardcoded.

→ The replenishment sheet staff uses every week

07

Payment Breakdown

Cash, card, UPI, PhonePe, Paytm, credit — aggregated by day from raw_sales_billwise.

→ Payment method dashboard chart

08

Customer Dimension

Normalizes four-plus mobile formats. Walk-in classification: NULL or names in CASH/WALK-IN/SUNDRY list → synthetic key 'WALK-IN'.

→ Foundation for Step 09

09

Customer Metrics

Per-customer spend, frequency, recency, preferred payment. One row per normalized mobile plus one WALK-IN row.

→ Customer analytics page

10

Product Associations

Basket analysis: self-join on bill_no. co_occurrences, support, confidence, lift. Minimum five co-occurrences. 30,018 pairs.

→ "Frequently bought together" recommendations

The critical dependency chain

Step 01's dense grid is not optional. It ensures no gaps in the time series so window functions see exactly the right rows. If Step 01 has a bug, Steps 02 through 10 produce silently wrong results. Every replenishment recommendation, every health flag, every demand forecast flows from that cross-join.

i.

PostgreSQL Window Functions

Tier I · SQL

Intuition. Normal SQL groups rows and collapses them (GROUP BY). Window functions look at neighboring rows without collapsing. Every input row produces one output row that can see its context.

AnalogyA spreadsheet column of daily sales where you want a "7-day rolling average" column next to each row. You don't want one average — you want each row to keep its identity while knowing its neighborhood.
Why it matters in AxonFlux

Steps 02, 03, 04 are entirely window functions. On 2.3 million rows, SQL window functions run in milliseconds. Equivalent Python loops would take minutes.

AVG(quantity_sold) OVER (
  PARTITION BY product_id      -- reset window per product
  ORDER BY sale_date           -- define sequence
  ROWS BETWEEN 6 PRECEDING    -- 7 rows including current
    AND CURRENT ROW
)
A critical distinction

ROWS BETWEEN 6 PRECEDING AND CURRENT ROW = 7 values including today. For ML features, you need ROWS BETWEEN 7 PRECEDING AND 1 PRECEDING — 7 values excluding today. This is the data leakage bug in Step 02.

Common mistakeConfusing ROWS BETWEEN (physical row count) with RANGE BETWEEN (value-based). For time series, almost always use ROWS — RANGE on dates can behave unexpectedly when there are ties.
ii.

Dense Time Series & the Date Spine

Tier I · SQL

Intuition. If a product had no sales on Sunday, there's no row for that product on Sunday. When you compute "7-day rolling average," Sunday's window has only six real days. The math is quietly wrong. Solution: generate a complete date list, cross-join with all products, LEFT JOIN actual sales. Products with no sales get quantity_sold = 0.

AnalogyA school attendance register. If you only record students who came, the register has gaps. To know "attended X of last 7 days," you need a full 7-day roster — including absent days.
The pattern, in Step 01 
WITH date_series AS (
  SELECT generate_series(
    MIN(sale_date), CURRENT_DATE, '1 day'::interval
  )::date AS d
  FROM derived.daily_sales_summary
),
products AS (
  SELECT DISTINCT barcode FROM raw.raw_sales_itemwise
),
dense_grid AS (
  SELECT d, barcode FROM date_series CROSS JOIN products
)
SELECT g.d, g.barcode,
  COALESCE(s.quantity_sold, 0) AS quantity_sold
FROM dense_grid g
LEFT JOIN aggregated_sales s
  ON s.sale_date = g.d AND s.barcode = g.barcode
Common mistakeINNER JOIN instead of LEFT JOIN when attaching sales data. The inner join silently drops zero-sales days and breaks every window function downstream.
iii.

Data Leakage in Time Series — resolved

Tier I · ML

Intuition. Leakage means your model trained with information it wouldn't have had at prediction time. In time series, the classic form is using future data to compute features for the past.

AnalogyGiving students the exam answers the night before, then being impressed they scored well. The test looks passed. Reality hasn't been tested.
The original problem

In 02_product_daily_features.sql, the rolling averages used ROWS BETWEEN 6 PRECEDING AND CURRENT ROW — seven values including today. When training a model with today's quantity as target, today's value sits inside the feature. The model trivially memorizes the answer.

The fix — additive, not replacing

Replacing the existing columns would have broken Step 03's operational WMA (which correctly uses today's value for current-state replenishment decisions — that's not leakage when there's no future target). So the fix added a parallel set of lagged columns alongside the originals:

-- Operational stats — include today (Step 03 WMA, replenishment)
AVG(quantity_sold) OVER (
  PARTITION BY product_id ORDER BY date
  ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
) AS last_7_day_avg

-- ML-safe stats — exclude today (B1 training features)
AVG(quantity_sold) OVER (
  PARTITION BY product_id ORDER BY date
  ROWS BETWEEN 7 PRECEDING AND 1 PRECEDING
) AS last_7_day_avg_lagged

Same pattern applied for last_30_day_avg_lagged, last_60_day_avg_lagged, and last_7_day_stddev_lagged. The stockout_proxy was switched to the lagged 7-day average — today's zero should not suppress the "recently active" signal it depends on.

Verification on live data

After rebuild: 2.92M rows in product_daily_features. 2.91M have lagged values populated (NULLs only on each product's first observed day — expected). 268,377 rows show a meaningful difference between current and lagged windows — the proof that the frames compute different things.

Spot-check on barcode 8909106084568, May 1 2026 with qty=128:

avg7 (inclusive) = 28.86 avg7_lag = 10.57 delta = 18.29

Without the fix, a model training to predict 128 would have been handed 28.86 as its "feature" — almost a third of the answer baked in. With the lagged column, it gets 10.57, which is what was actually knowable before May 1.

The general principle, restated

Two different consumers, two different windows. Operations needs the inclusive frame because "today's running average through right now" is a legitimate signal for current-state decisions. ML training needs the lagged frame because the target itself sits at "today" and any feature touching today is leakage. Keeping both in the same table — clearly named — makes the distinction explicit at every query site.

What changed downstreamStep 03 still references last_7_day_avg (non-lagged). WMA predictions are byte-identical to before. Frontend dashboards, replenishment sheet, health flags — all unchanged. The only difference is that B1 now has clean features to train on.
iv.

Walk-Forward Validation

Tier I · ML

Intuition. You can't randomly split test data for time series forecasting. If January is your test set, you have December in training. In production you'd never predict January using data from both November AND March. Random splits break temporal causality.

AnalogyStock market backtesting. You simulate as if you only knew the past. Any peekback at future prices makes the backtest useless — even if it makes the strategy look brilliant.
The correct approach 
# Walk-forward (expanding window)
Train: Jan–Jun  | Test: Jul
Train: Jan–Jul  | Test: Aug
Train: Jan–Aug  | Test: Sep
...

# Each fold expands training forward.
# Test is always strictly after train.
# sklearn.model_selection.TimeSeriesSplit

For B1 specifically: minimum 90 days training (lag_60 plus buffer). With 730 days of data, ~8 folds. The average MAPE across folds is your honest error rate.

Critical mistakeUsing sklearn.model_selection.train_test_split on time series. It shuffles randomly. The model will look accurate and completely fail in production.
v.

Weighted Moving Average — Mechanics & Limits

Tier I · ML

The formula in Step 03:

predicted_demand = GREATEST(
  0.6 × last_7_day_avg
  + 0.3 × last_30_day_avg
  + 0.1 × last_60_day_avg,
  0.02  -- floor to avoid division by zero in Step 06
)
AnalogyAsking three advisors what temperature to dress for. You trust the one who checked this morning (0.6) more than the one who looked at last year's averages (0.1).
What the 0.02 floor actually does

Prevents division by zero when computing days_of_cover = stock ÷ demand in Step 06. But a consequence: a permanently discontinued product still generates reorder recommendations forever. Staff following the sheet blindly will order things no longer sold. This is an embedded business decision, not just a math fix.

What WMA gets wrong
No seasonality capture Weights not validated New products inflated Can't distinguish stockout from price-too-high Misses step changes from promotions
vi.

FastAPI Dependency Injection

Tier I · Backend

Intuition. Depends() is FastAPI's way of saying: before this endpoint runs, run this other function first and inject the result. It's declarative middleware per-endpoint. The power is composability — chain dependencies, share logic, handle cleanup automatically.

# Two patterns in AxonFlux
async def get_conn():
    # Generator: code before yield = setup, after = cleanup
    conn = engine.connect()
    try:
        yield conn         # request handler runs here
    finally:
        conn.close()      # after response is sent

async def get_current_user(token = Depends(oauth2_scheme)):
    payload = jwt.decode(token, SECRET_KEY)
    return payload
Why two connection patterns

get_conn() returns a raw engine connection — used for derived.* and raw.* queries written as text() SQL. get_db() returns a SQLAlchemy ORM session — used for app.* writes where type safety and relationship management matter.

Failure modeIf an exception occurs inside a request and the dependency uses try/finally, FastAPI still runs the finally. But if the dependency uses plain return (not yield), the connection is never closed on exception. Connection leak waiting to happen.
vii.

Basket Analysis — Support / Confidence / Lift

Tier II · ML

Intuition. Which products are bought together? Count co-occurrences in transaction records. No fancy algorithm needed at this scale — just a SQL self-join on bill_no.

The SQL pattern in Step 10 
SELECT a.barcode AS barcode_a, b.barcode AS barcode_b,
       COUNT(*) AS co_occurrences
FROM raw.raw_sales_itemwise a
JOIN raw.raw_sales_itemwise b
  ON a.bill_no = b.bill_no   -- same transaction
 AND a.barcode < b.barcode   -- avoid duplicates
GROUP BY a.barcode, b.barcode
HAVING COUNT(*) >= 5
Metrics

Support(A,B) = count(A∩B) ÷ total_transactions — how common is this pair overall.
Confidence(A→B) = count(A∩B) ÷ count(A) — if bought A, what % also bought B.
Lift(A,B) = confidence ÷ support(B) — how much more likely is B given A vs B in general.

Lift = 1.0 means independent. Lift > 1.0 means positive association. Lift > 3.0 is usually a strong signal worth recommending.

Hidden assumptionThe self-join on bill_no assumes bill_no is unique per shopping trip. If Er4u reuses bill numbers across days, associations become meaningless noise. Worth verifying with a simple count query.
viii.

The COALESCE Enrichment Pattern

Tier I · Architecture

Intuition. app.* data should override derived.* at query time — never by modifying derived tables (which get truncated every rebuild). COALESCE picks the first non-NULL value, so if app.products has a canonical_name, use it; otherwise fall back to the derived name.

-- Every product query in the API uses this pattern
COALESCE(p.canonical_name, d.product_name) AS display_name
-- p = app.products (human-authored, may be NULL)
-- d = derived.product_dimension (always populated)
Why not just update derived.*?

Because derived.* is truncated on every pipeline run. Any direct edits are lost. The three-schema separation exists precisely so that human-authored overrides live in app.*, which Alembic manages and which survives rebuilds.

AnalogyA library catalog (derived) with sticky notes (app overrides). The catalog gets reprinted every week. The sticky notes survive — they're in a separate folder. When looking up a book, you check the sticky note first.
Dangerous assumptionIf you ever write UPDATE statements on derived.* tables directly (bypassing the pipeline), those changes are silently wiped on the next rebuild. No warning. This is why "never modify derived.*" is non-negotiable.
ix.

Append-Only + Full Rebuild Architecture

Tier I · Data Engineering

Intuition. Two fundamental patterns in deliberate tension. raw.* is append-only (no updates, ever). derived.* is truncate-and-rebuild (wiped clean, rebuilt from scratch on every run). Together they create a system that is both auditable AND always consistent.

Why append-only for raw.*?

Every ingestion creates an immutable audit trail. You can always answer "what data did we have on March 15?" by querying raw.* with import_batch_id created before that date. If you UPDATE or DELETE from raw.*, this auditability is destroyed forever.

Why full rebuild for derived.*?

Analytics tables have complex dependencies (01 → 02 → 03 → 06). If you try to incrementally update them ("add only today's rows"), you face every edge case: what if a historical row changed? What if an alias was remapped? What if a formula changed? Full rebuild avoids it all — throw away derived.* and recompute.

Analogyraw.* is the court transcript — append-only, legally unchangeable. derived.* is the lawyer's summary notes — thrown away and rewritten before each hearing, always derived fresh from the transcript.

This works at 2.3M rows in minutes. At 10× volume or with daily rebuild requirements, you'd need incremental processing (dbt, Spark, partitioned rebuilds). The current architecture is correct for the scale — but know when it stops working.

x.

The Pipeline Subprocess Pattern

Tier II · Systems

Intuition. The weekly pipeline is long-running, file-touching, DB-heavy. If it ran inside the FastAPI event loop it would block every other API request for minutes. By running it as a subprocess, it gets its own memory, process space, and error scope — and the API stays responsive.

# api/routers/pipeline.py (simplified)
process = subprocess.Popen(
    ["python", "pipelines/weekly_pipeline.py"],
    stdout=subprocess.PIPE,
    stderr=subprocess.STDOUT
)
# Store PID in DB for status polling + cancellation
run_id = store_run(pid=process.pid, status="running")
Why not async?

FastAPI is async, but the pipeline uses synchronous psycopg2 and pandas (both blocking). Running a blocking operation in an async event loop blocks every other request on that thread. Subprocess sidesteps the issue entirely.

Failure scenarioIf the pipeline crashes at Step 4, TRUNCATE for steps 0–3 has committed but INSERT for 4–10 hasn't run. derived.product_health_signals is empty. The next frontend load shows zero replenishment items. Staff think the system is broken. Fix: wrap the rebuild in one transaction, or use a schema-swap pattern (build into derived_staging, then RENAME).
xi.

SQLAlchemy 2.0 — ORM vs Core

Tier II · Backend

Intuition. SQLAlchemy has two modes. ORM maps Python classes to database tables — you work with objects, relationships, the ORM emits SQL. Core is lower-level — you write SQL expressions (or raw text()) and get rows back. AxonFlux uses both, deliberately.

ORM — for app.* writes 
product = db.query(AppProduct).filter(
    AppProduct.barcode == barcode
).first()
if not product:
    product = AppProduct(barcode=barcode)
    db.add(product)
product.canonical_name = new_name
db.commit()
Core — for derived.* reads 
result = conn.execute(text("""
  SELECT p.barcode, COALESCE(a.canonical_name, p.product_name)
  FROM derived.product_health_signals p
  LEFT JOIN app.products a ON a.barcode = p.barcode
  WHERE p.flag = :flag
"""), {"flag": flag})

derived.* tables are rebuilt on every pipeline run — keeping ORM models in sync with them would mean model changes every time a column is added. Raw text() SQL is more flexible for analytics reads. ORM adds safety where you actually need mutations (app.*).

Lazy loading trapAccessing a relationship attribute on an ORM object after the session closes raises DetachedInstanceError. Example: load a Product, close session, access product.aliases — SQLAlchemy tries to query with a closed session. Fix: use eager loading (joinedload) or access attributes while session is open.

What's missing or weak

No pipeline transaction wrapping. If the 10-step rebuild fails at step 4, you have partial derived tables. A senior engineer would wrap the full rebuild in a single transaction or use a schema-swap pattern.

No data quality layer. SHA-256 dedup exists, but row-level validation does not. Negative quantities, zero prices, malformed dates all enter raw tables silently and propagate.

No monitoring or alerting. The pipeline can produce zero rows in product_daily_metrics (if date parsing breaks). Nobody would know until staff notice wrong dashboard numbers.

Feature documentation is absent. Every column in derived.product_daily_features is a computed assumption. Stockout proxy logic, WMA weights, threshold values — none documented in code or docs.

No evaluation infrastructure. Before B1, there's no framework to ask "is XGBoost actually better than WMA on this dataset?" No baseline metrics collected, no backtesting harness, no MLflow runs with WMA as a baseline.
